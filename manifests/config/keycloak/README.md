# keycloak

Red Hat build of Keycloak (RHBK) — an OIDC provider for the lab, with its
PostgreSQL managed by CloudNativePG.

## Pieces

| What | Where | Why |
|---|---|---|
| `rhbk-operator` | `manifests/olm/keycloak` | OwnNamespace/SingleNamespace **only** — the OperatorGroup must set `targetNamespaces` |
| `cloudnative-pg` | `manifests/olm/cloudnative-pg` | **AllNamespaces** — it manages a Cluster in the `keycloak` namespace, not its own |
| `Cluster/keycloak-db` | `base/postgres-cluster.yaml` | Keycloak in production mode requires an external database; the RHBK operator does not provide one |
| `Keycloak/keycloak` | `base/keycloak.yaml` | the instance |
| `Certificate`, `Route` | `overlays/hub` | TLS terminated at the pod, passthrough Route |

The two operators need **opposite** OperatorGroup shapes. That is not an
inconsistency — it follows from what each supports and what each has to reach.
`scripts/verify-channels.sh` checks both against the channel each Subscription
pins.

## How the database is wired

CloudNativePG creates, for a `Cluster` named `keycloak-db`:

| Resource | Purpose |
|---|---|
| `keycloak-db-rw` Service | always routes to the current primary |
| `keycloak-db-ro` Service | replicas only |
| `keycloak-db-app` Secret | `username` / `password` for the application user |

`spec.db` in the Keycloak CR points at the `-rw` Service and that Secret, so a
failover is invisible to Keycloak — it keeps talking to `keycloak-db-rw` and
CloudNativePG repoints it.

No database credential is written in this repo. CloudNativePG generates it, and
Keycloak reads it by reference.

`storageClass` is deliberately omitted from the Cluster so it uses the cluster
default — set to `ocs-storagecluster-ceph-rbd` by
[manifests/config/odf](../odf). That keeps the base free of cluster-specific
values.

## The hostname is the OIDC issuer URL

`keycloak.apps.hub.lab.bewley.net` is set by the overlay, not defaulted in base,
because it is both cluster-specific and **expensive to change**. It becomes the
OIDC issuer URL, which is embedded in every token Keycloak signs and in every
client's configuration. Changing it later invalidates all of them.

Decide it deliberately before the first client is configured.

## TLS terminates at Keycloak, not at the router

The `Route` is `passthrough`: the router forwards TLS untouched and the Keycloak
pod terminates it using `keycloak-tls`, issued by the `homelab-ca` ClusterIssuer
from [cert-manager](../cert-manager). The router's own wildcard is not involved.

For an ordinary app, edge termination at the router is simpler and fine. For an
identity provider it is worth the extra step — the router-to-pod hop is
encrypted too, rather than plaintext inside the cluster.

The certificate covers both the external name and `keycloak-service.keycloak.svc`,
so in-cluster clients talking to the Service directly also get a valid cert.

`spec.ingress.enabled: false` because the operator would otherwise create an
Ingress that OpenShift converts to a Route by rules that are harder to reason
about than simply writing the Route.

## Order of operations

Sync waves order things inside this Application:

```
0   Cluster/keycloak-db      Postgres comes up, creates keycloak-db-app
5   Certificate/keycloak     produces keycloak-tls
10  Keycloak/keycloak        needs both of the above
15  Route/keycloak           needs the Service the operator creates
```

Across Applications there is no wave ordering — `cloudnative-pg`, `cert-manager`
and this are separate Applications generated by ApplicationSets, so
`hub-cfg-keycloak` fails and retries until the CRDs exist and `homelab-ca` is
Ready. Expect red on first sync; it converges.

## Verifying

```bash
oc get cluster.postgresql.cnpg.io -n keycloak
```

Wait for `keycloak-db` to report a primary and `Cluster in healthy state`.

```bash
oc get keycloak,certificate,route -n keycloak
```

Then reach it — the CA must be trusted first, see
[cert-manager](../cert-manager):

```bash
oc get route keycloak -n keycloak -o jsonpath='https://{.spec.host}/realms/master/.well-known/openid-configuration{"\n"}'
```

That URL is the OIDC discovery document. If it returns JSON with the right
`issuer`, Keycloak is serving correctly.

The initial admin credentials are generated by the operator:

```bash
oc get secret keycloak-initial-admin -n keycloak -o jsonpath='{.data.username}' | base64 -d; echo
oc get secret keycloak-initial-admin -n keycloak -o jsonpath='{.data.password}' | base64 -d; echo
```

## The `homelab` realm

`overlays/hub/realm-homelab.yaml` declares one realm for the whole lab, with
**one client per cluster**. Realm-per-cluster was rejected: it duplicates every
user into every realm, which defeats central identity.

A realm is an isolated tenant — its own users, groups, roles, policy, signing
keys and issuer URL. Users cannot cross realms. A **client** is one application
registered inside a realm, which is why several clusters share one realm rather
than getting one each.

`master` is left alone. It is Keycloak's own administrative realm; putting
applications or end users there places them adjacent to the admin surface.

The realm name is part of the issuer URL —
`https://keycloak.apps.hub.lab.bewley.net/realms/homelab` — so it is as
expensive to change as the hostname.

### Why it lives in `overlays/hub`

Keycloak runs only on hub, so the realm exists only here. Other clusters do not
import it; they point at it as a remote OIDC issuer. **A second cluster's client
is added to the `clients` list in this file**, not to a realm import on that
cluster.

### The client, and the name that must match

`ocp-hub` is a confidential client. OpenShift's openID identity provider
requires a client secret, so a public/PKCE client is not available:

```
spec.identityProviders[0].openID.clientSecret.name: Required value
```

Its redirect URI ends in the **identity provider name**, not the client ID:

```
https://oauth-openshift.apps.hub.lab.bewley.net/oauth2callback/keycloak
                                                              ^^^^^^^^
```

That segment must equal `identityProviders[].name` in the OAuth CR. Change one
without the other and login fails with a `redirect_uri` mismatch that names
neither side.

The `groups` protocol mapper is not optional. Without it the token carries no
group information and every user authenticates with no group membership at all.

### Secrets: placeholders, not committed values

The realm JSON uses `${VAR}` placeholders. The operator turns each
`spec.placeholders` entry into an environment variable sourced from a Secret,
and Keycloak substitutes it during import — so the secret is never in git.

One 1Password item feeds it, via the ExternalSecret machinery already in place.

**Manual step — create the item first.** In the `eso` vault, `keycloak-homelab`
with one field per value below:

| Field | Purpose |
|---|---|
| `ocp-hub-client-secret` | shared with OpenShift's OAuth server |
| `admin-password` | `dlbewley`, the `cluster-admins` account |
| `dev1-password` … `dev3-password` | test accounts in `developers` |
| `alice-password`, `bob-password` | test accounts in `developers` |

`op` generates the values, so nothing has to be invented:

```bash
op item create --category=login --vault=eso --title=keycloak-homelab \
  'ocp-hub-client-secret[password]=generate' \
  'admin-password[password]=generate' \
  'dev1-password[password]=generate' \
  'dev2-password[password]=generate' \
  'dev3-password[password]=generate' \
  'alice-password[password]=generate' \
  'bob-password[password]=generate'
```

Read one back when you need to log in as that account:

```bash
op read 'op://eso/keycloak-homelab/dev1-password'
```

### Test accounts

`dev1`, `dev2`, `dev3`, `alice` and `bob` exist for later testing. All are in
`developers` and **none is in `cluster-admins`** — `developers` grants nothing
in OpenShift until a Group of that name and a binding exist, so these accounts
can authenticate and do nothing, which is what makes them useful for testing
the claim.

They use `temporary: false`, unlike a real onboarding flow. A temporary password
is rotated away at first login, which would leave the 1Password value stale and
the account unusable for the next test.

Every credential carries a `value`. A password credential without one is
accepted by the API and reported Synced by ArgoCD — `value` is not a required
field — so the realm imports "successfully" and the account simply cannot log
in.

Until that exists the ExternalSecret reports `SecretSyncedError` and the realm
import waits. Expected order, not a fault.

The same client secret will be needed again as a Secret in `openshift-config`
when the OAuth CR is wired up — one source, two consumers.

### Import-on-create, not reconciliation

`KeycloakRealmImport` imports once. Editing the CR does **not** reliably
re-import into an existing realm, so it is less declarative than it looks. To
force a re-import:

```bash
oc delete keycloakrealmimport homelab -n keycloak
```

ArgoCD recreates it. Treat the admin console as read-only for anything declared
here, or git and reality will disagree with no warning.

### Verifying

```bash
oc get keycloakrealmimport homelab -n keycloak -o jsonpath='{.status.conditions}' | jq
```

```bash
curl -sS --cacert <(oc extract secret/homelab-ca-tls -n cert-manager --keys=tls.crt --to=-) \
  https://keycloak.apps.hub.lab.bewley.net/realms/homelab/.well-known/openid-configuration | jq -r .issuer
```

Should print the `homelab` issuer URL.

## Not done here

**Wiring OpenShift to it.** The realm and client exist, but `oauth/cluster` has
no `identityProviders` entry yet, so `kubeadmin` is still the only login path.
That is `homelab-2026-4pq.8`, deliberately separate so this change cannot affect
login.

**Backups.** CloudNativePG supports scheduled backups and point-in-time recovery
to S3, which the ODF object store could serve. Not configured; the database is
currently protected only by Ceph replication, which is not a backup.

**SPIFFE/SPIRE.** The reason the hostname and TLS choices above matter. SPIRE
federation depends on a stable, trusted issuer URL, so both were fixed
deliberately rather than left to default.
